MQTT

MQTT est un protocole réseau léger de type "publish-subscribe".

Message : Communication d'information
Queuing : Pas une communication directe. Délai possible
Telemetry : Mesuré à distance, du Grec tele (à distance) metron (mesurer)
Transport : Objectif est de transporter le message

Objectifs du protocole MQTT

  • Optimisé pour les appareils de type IdO
    • Simplicité
    • Réduction des transferts réseau
    • Optimisation énergétique
  • Assurance de transmission variable
    • Stabilité en cas d'internet instable

Prouvé sur le marché

  • Facebook messenger (sur mobile)
  • Philips Hue (lumières intelligentes)
  • Tesla, Ford, Audi ...
  • Google Nest (thermostats, caméras ...)
  • Sonos (Hautparleurs)
  • Honeywell (Gestion industrielle)

Et plusieurs autres!

Terminologie MQTT

Broker (courtier): L'entité centrale qui relaie les messages.

Client: Tout ce qui se connecte au "Broker"— Capteurs, applications, ...

Topic (sujet): Un filtre de contenu (e.x. "maison/salon/temperature").

Publish (publier): Un client envoie un message au Broker sur un Topic

Subscribe (souscrire): Un client demande d'être notifié par le Broker lorsqu'un topic reçoit un message

De façon plus technique

  • Connexion TCP
  • Librairie dans la majorité des langages
  • Possibilité de passer par les Websockets pour le Web
  • Filtres automatiques avec les "Topics"
  • Assurance de suivi avec les niveaux QoS

Les 3 niveaux de QoS (qualité de service)

QoS 0

  • Envoi le message une fois, sans confirmation. Si le message n'est pas reçu, il est perdu.
  • Très efficace en termes de transfert réseau et d'énergie.
  • Analogie: Tu parles à quelqu'un dans une pièce bruyante et espères être entendu.

QoS 1

  • Le client envoyant le message le garde et le renvoi jusqu'à avoir une confirmation du Broker.
  • Duplication des messages possible.
  • Analogie: Un parent te repose la même question jusqu'à ce que tu dises : "Oui, j'ai compris".

QoS 2

  • Le client et le Broker s'assurent à l'aide de plusieurs (4) allez-retour que le message s'est bien rendu et est traité une seule fois.
  • Analogie: Un colis Amazon qui nécessite la signature à la réception par la personne qui reçoit ET le livreur.

La compétition

MQTT

  • Simple
  • Efficace (énergie et réseau)
  • En mémoire

Kafka

  • Infrastructure complexe
  • Gestion de grand volume (millions de requêtes par secondes)
  • Permanent sur le disque

Polling HTTP

  • Peu efficace
  • Gestion manuelle
  • Optimisations personalisées

Variables

Il est possible d'utiliser des variables "permanentes".

  • context : Local au node lui-même
  • flow : Local au flow
  • global : Global pour l'ensemble des flows

Par exemple:

flow.set("compteur", 123)
flow.get("compteur")

Fonctions

  • Une fonction doit toujours retourner le message (donc msg et pas juste le payload!).
  • Il est possible de configurer plusieurs sorties. Il faudra alors que le return soit un tableau.
    • Pour cloner un message, on utilise RED.util.cloneMessage()
  • On peut débugger une fonction avec node.warn plutôt que console.log
